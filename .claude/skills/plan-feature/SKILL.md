Составь план реализации фичи: $ARGUMENTS

## Перед планированием (только чтение, код НЕ менять)
1. Прочитай `docs/adr/` (ADR-001..003), `src/shared/types.ts`, `manifest.json`, `package.json`.
2. Изучи затронутые файлы через Glob/Grep/Read.
3. Проверь, есть ли в `package.json` скрипт `test`. Если нет — Этап 2 включает установку `vitest`
   и добавление `"test": "vitest run"`.

## Структура плана: до 4 атомарных этапов (= 4 git-коммита)
Если этап фиче не нужен — пометь его «N/A — пропуск» с причиной, не выдумывай работу.

- **Этап 1 (Контракты):** ТОЛЬКО типы в `src/shared/types.ts` (+ `manifest.json` при новых
  permissions/entry). Никакого runtime-кода: `types.ts` — только типы.
- **Этап 2 (Тесты — TDD):** `*.test.ts` на чистые функции, парсинг, валидацию, граничные случаи
  + заглушки сигнатур (`throw new Error('not implemented')`) в `src/shared/*`, чтобы `tsc -b`
  оставался зелёным. Тесты при этом ожидаемо красные. Обязательно, если затронуто:
  тест «hint не содержит исправленную форму» и тест якорения по `quote` через `indexOf`.
- **Этап 3 (Логика):** реализация в `src/shared/*`, `src/background/*`, `src/content/*`
  (zod-схемы и валидаторы — здесь, не в `types.ts`). Все тесты Этапа 2 зелёные.
- **Этап 4 (UI):** Shadow DOM (`attachShadow({ mode: 'closed' })`, один host-элемент, без глобального
  CSS) или Popup (`src/main.tsx`, `src/App.tsx`).

Для КАЖДОГО этапа укажи:
1. Белый список файлов, которые можно менять, и явно — что трогать запрещено.
2. Верификацию: `npm run build` + `npm run lint` (+ `npm test` с Этапа 2; ручная проверка в Chrome для Этапа 4).
3. Сообщение коммита в стиле conventional commits (`feat:`, `test:`, `chore:`, `docs:`).
4. Чек инвариантов, относящихся к этапу:
   - NO AUTO-REWRITE: нет `value =`, `execCommand('insertText')`, `textContent =` на полях хоста,
     нет кнопок Fix/Apply/Accept;
   - hint без ответа (фильтр в `src/shared/issue-filter.ts`);
   - якорение по `quote`, никогда по оффсетам от LLM;
   - API-ключ только в background; никакого состояния в переменных модуля service worker;
   - новые entry-файлы манифеста — с уникальными basename;
   - не читать password/email поля.

## Исполнение
После вывода плана ОСТАНОВИСЬ и жди команды на старт Этапа 1.
Выполняй строго по одному этапу. По завершении этапа покажи `git diff --stat`, результат
верификации и предложенное сообщение коммита — и жди «commit» / «next» от пользователя.
Не коммить и не переходи к следующему этапу без явной команды.
