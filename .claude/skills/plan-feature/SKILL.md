Составь план реализации фичи: $ARGUMENTS

Результат работы — ТОЛЬКО файл `.claude/current-plan.md` (перезаписать, если существует).
Код, ADR, конфиги в этой сессии НЕ менять. План будет исполнять другая сессия (модель Sonnet)
без доступа к контексту этой сессии — файл должен быть самодостаточным.

## Перед планированием (только чтение)
1. Прочитай все файлы в `docs/adr/`, `src/shared/types.ts`, `manifest.json`, `package.json`.
2. Изучи затронутые файлы через Glob/Grep/Read. Если охват неясен или затронуто больше
   ~3 областей (content / background / shared / popup), сначала запусти 1–2 субагента `Explore`
   параллельно, каждому — свою область и вопрос «где и как это сделано сейчас, какие хелперы
   переиспользовать». Ключевые файлы (`types.ts`, затронутые ADR, файлы из белых списков)
   всё равно прочитай сам: план опирается на точный текст, а не на пересказ.
3. Проверь, есть ли в `package.json` скрипт `test`. Если нет — Этап 2 включает установку `vitest`
   и добавление `"test": "vitest run"`.
4. Определи влияние на ADR:
   - какие существующие ADR фича затрагивает (описание «Сейчас…» устарело, новый файл/хелпер
     в зоне ответственности ADR, новое ограничение «Запрещено»);
   - нужен ли НОВЫЙ ADR. Критерии: новый слой/модуль с собственным контрактом, новое permission
     или entry в manifest, новый способ хранения/обмена сообщениями, выбор между альтернативами,
     который позже захочется оспорить. Мелкие детали реализации ADR не требуют.
5. Все архитектурные решения прими здесь. Исполнитель не должен выбирать между вариантами:
   если есть развилка — зафиксируй выбор в плане (и в ADR на Этапе 0).

## Структура плана: до 5 атомарных этапов (= 5 git-коммитов)
Если этап фиче не нужен — пометь его «N/A — пропуск» с причиной, не выдумывай работу.

- **Этап 0 (Решения / ADR):** только `docs/adr/*.md` (+ ссылка в разделе «Contract First» `CLAUDE.md`
  при новом ADR). Новый ADR: имя `ADR-NNN-kebab-title.md` (следующий номер), разделы
  **Статус / Контекст / Решение / Запрещено**, язык и стиль как у существующих. Правка существующего:
  обновить «Решение», при необходимости «Запрещено»; отменённое решение — `Статус: Заменено ADR-NNN`,
  файл не удалять. Коммит `docs:`. Если архитектура не меняется — «N/A — пропуск».
- **Этап 1 (Контракты):** ТОЛЬКО типы в `src/shared/types.ts` (+ `manifest.json` при новых
  permissions/entry). Никакого runtime-кода: `types.ts` — только типы.
- **Этап 2 (Тесты — TDD):** `*.test.ts` на чистые функции, парсинг, валидацию, граничные случаи
  + заглушки сигнатур (`throw new Error('not implemented')`) в `src/shared/*`, чтобы `tsc -b`
  оставался зелёным. Тесты при этом ожидаемо красные. Обязательно, если затронуто:
  тест «hint не содержит исправленную форму» и тест якорения по `quote` через `indexOf`.
- **Этап 3 (Логика):** реализация в `src/shared/*`, `src/background/*`, `src/content/*`
  (zod-схемы и валидаторы — здесь, не в `types.ts`). Все тесты Этапа 2 зелёные.
- **Этап 4 (UI):** Shadow DOM (`attachShadow({ mode: 'closed' })`, один host-элемент, без глобального
  CSS) или Popup (`src/main.tsx`, `src/App.tsx`).

## Правила записи под исполнителя-Sonnet
- Конкретика вместо описаний: точные пути, имена функций/типов, полные сигнатуры.
  Новые типы Этапа 1 и сигнатуры заглушек Этапа 2 — готовыми блоками кода TypeScript.
- Тест-кейсы Этапа 2 — списком: `имя теста` → вход → ожидаемый результат.
- Шаги этапа — нумерованные императивы («Добавь…», «Экспортируй…»), один шаг = одно действие
  в одном файле. Без рассуждений и альтернатив; обоснование — максимум одна строка «Зачем».
- Указывай, какие существующие хелперы переиспользовать (путь + имя), чтобы исполнитель
  не писал дубликаты.
- Ссылайся на якоря в коде по имени символа/строке-ориентиру, а не по номерам строк
  (номера сдвигаются между этапами).
- Чек инвариантов — только относящиеся к этапу (источник: Product Invariants / UI Isolation /
  Gotchas в `CLAUDE.md` и раздел «Запрещено» ADR), чекбоксами, проверяемыми грепом/чтением.
  Не копируй общий список инвариантов в план: `CLAUDE.md` загружается в сессию исполнителя сам.
- Правила исполнения (протокол, commit/next) в план не пиши — они в скилле `create-planned-feature`.
- Без воды: никаких вступлений, повторов CLAUDE.md, общих советов.
